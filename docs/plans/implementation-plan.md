## 진행 원칙

- 단계 0 완료, 단계 1 모델 선택은 Decider-2B Q4_K_M 채택으로 완료했다. 2026-11-13 사용자 승인으로 단계 2를 진행한다. 품질·지연 한계는 남아 있으며 단계 2 체크박스는 검증 전 미완료로 유지한다. 운영 배포에는 별도 승인이 필요하다.
- 사용자와 한 단계씩 진행한다. 해당 단계의 목표·변경 범위 → 구현 또는 실험 → 좁은 검증 → 결과 보고 순서로 수행하고 다음 단계 실행 요청을 기다린다.
- 단계 내부의 구현·검증은 완료 조건까지 수행한다. 실패를 확인한 경우 원인을 해결하거나 설계 변경이 필요한 이유를 제시하며 완료로 표시하지 않는다.
- 사용자 판단이 필요한 제품 범위·보안·운영 선택만 질문한다. 코드·문서·환경으로 확인 가능한 내용은 직접 확인한다.
- `develop`에서 작업한다. 사용자 변경을 보존하고 커밋·푸시는 별도 요청이 있을 때만 한다.
- 검증용 파일·컨테이너·볼륨도 생성·정리 범위를 설명한다. 삭제·덮어쓰기·초기화는 승인 없이 실행하지 않는다. 운영 데이터로 실험하지 않는다.
- 중요한 로직에는 한글로 이유와 제약을 주석에 남긴다. 결과의 장기 지식은 Wiki에, 요구사항 변경은 PRD에 반영한다. 작업 상태는 이 문서에서만 관리한다.

## 단계 0 — 개발 환경과 실험 경계

- [x] Rust 도구체인, Docker 엔진 연결, `docker compose` 사용 가능 여부와 amd64 환경을 확인한다.
- [x] 실행할 프로젝트·포트·환경 변수·개발용 데이터 위치를 정한다. 비밀값이 없는 설정 예시와 로컬/운영 분리 원칙을 준비한다.
- [x] 설치·수정이 필요한 항목은 현재 상태와 변경 범위를 설명한다. 이미 보고된 설치 직후 실패를 재현하려는 것이 아니라 초기 화면 진행 이후의 현재 상태를 확인한다.

**산출물:** 개발 실행 전제와 확인 결과. 아직 전체 앱을 만들지 않는다.

**완료 조건:** Docker 엔진과 Compose를 실제 사용할 수 있고 이후 실험의 자원·데이터 경계가 명확하다. 불가능하면 원인을 해소하거나 환경 작업만 남았음을 보고한다.

### 단계 0 결과

- 판정: 완료. 앱 구현·컨테이너 실행 검증은 아직 수행하지 않았다.
- 환경: `develop`, Intel Mac `Darwin x86_64`, Rust 기본 도구체인 `1.95.0-x86_64-apple-darwin`. `rustc --version`과 `cargo --version` 모두 1.95.0이며 `rustup component list --installed`에서 rustfmt·Clippy를 확인했다.
- Docker: 최초 확인에서 Desktop 소켓이 없어 `open -a Docker`로 설치된 Desktop을 실행했다. 이후 `docker version`에서 Client/Engine 29.9.3, Desktop 4.99.0, 서버 `linux/amd64` 연결을 확인했다.
- Compose: `docker compose version`은 v5.7.0. Desktop 실행 후 `docker compose ls --format json`이 성공하고 `[]`를 반환했다. 실행 중인 Compose 프로젝트는 없었으며 이 결과는 컨테이너 실행 성공을 뜻하지 않는다.
- 자원: `docker info`가 CPU 12개, 메모리 8,321,810,432 bytes를 보고했다. 이는 Docker VM 가용 설정이며 Laya 실행 가능성이나 Oracle 자원을 보장하지 않는다.
- 포트: `lsof`로 검사한 시점에 18080·18081 TCP 포트의 LISTEN 항목이 없었다. 향후 실행 전 다시 충돌을 확인한다.
- 산출물: [설정 예시](../../.env.example), [로컬 제외 규칙](../../.gitignore), [로컬 개발 환경](../wiki/local-development.md). 추가 설치·도구체인 변경·실제 `.env`·DB·컨테이너·볼륨 생성이나 삭제는 하지 않았다. Docker Desktop은 실행 상태로 둔다.
- 다음: 사용자 요청 시 단계 1에서 실제 Laya·OMP 계약을 검증한다.

## 단계 1 — 추론 후보·OMP 계약과 품질 검증

- [x] 공식 Laya의 사용할 리비전·라이선스·모델 배포 조건·CPU/ARM 지원 조건을 확인한다. ARM은 공식 구성 확인이며 실제 실행은 미검증이다.
- [x] OMP 설치 버전 18.19.0과 동일 버전 공식 태그의 실제 소스로 TypeSafe 호출 경로·인증·요청/응답 필드를 확인한다. 설치 바이너리의 종단 실행과 구분한다.
- [x] Python 추론 서버를 격리된 로컬 환경에서 실행하고 실제 모델 목록·판단 응답·오류를 관측한다. 모델 목록은 404로 확인했다.
- [x] OMP 계약과 Laya 계약의 필드·모델 선택·confidence·오류 차이를 정리하고 초기 Gateway 매핑을 문서화했다. [API 계약](../api-contract.md)을 PRD에 연결했다.
- [x] 한국어·영어 합성 입력의 평가 기준과 결과를 기록한다. score 품질 통과선은 미달이며 일반적인 제품 작업의 품질로 확대 해석하지 않는다.
- [x] 모델 크기·메모리·시작 시간·CPU 제약의 초기 근거를 수집한다. amd64 측정은 ARM 성능으로 일반화하지 않는다.

**산출물:** 실제 응답에 근거한 API 계약, 품질 평가 초안, 고정할 버전과 한계.

**완료 조건:** 실제 추론이 성공하고 OMP 호환 가능 범위와 변환 규칙이 명확하다. 필수 필드의 의미를 알 수 없거나 품질이 목적에 맞지 않으면 후속 구현 전에 재검토한다. 가짜 응답으로 통과시키지 않는다.

### 단계 1 결과

- 최종 판정: **단계 1 선택 완료 · Decider Q4 채택 · 단계 2 진행 승인(2026-11-13)**. 체크박스는 조사·실험 수행을 뜻하며 출시 수용이 아니다. 아래 Laya·Q8 기록의 당시 미승인 상태와 현재 결정을 구분한다.
- 변경: `experiments/stage1/`에 CPU 이미지·합성 평가 시나리오·재현 절차, `docs/api-contract.md`에 초기 계약을 작성했다. 실제 키·OMP 설정·운영 데이터는 변경하지 않았다.
- 검증: 고정 Laya 0.4.31 소스 이미지 빌드와 `pip check` 성공. 네트워크 없는 Linux amd64 컨테이너에서 실제 다국어 모델을 로딩하고 HTTP 추론·인증·오류 검사를 실행했다.
- 품질: 사전 통과선 대비 choice 11/12와 noul 4/4는 탐색 통과, score 1/3은 미달. 평가 명령은 이를 숨기지 않고 종료 코드 2를 반환했다.
- 계약: Laya에는 `/v1/models`가 없고 unknown bare-model은 자동 라우팅됐다. Gateway의 명시적 모델 목록·허용 목록·confidence 의미 보존이 필요하다.
- 위험: 읽기 전용 tokenizer 패치 경고는 발생했지만 원본 그대로 로딩·추론했다. OMP 실제 종단 실행·Oracle ARM·장문·실제 코딩 판단·복제본 성능은 미검증이다.
- 문서: [현재 추론 지식](../wiki/inference.md), [실행 근거·환경·보존 자원](../wiki/history/2026-11-12-laya-cpu-evaluation.md).
- 후속 결정: 비교 후 Decider Q4를 채택하고 품질·지연 위험을 명시한 단계 2 인프라 검증을 진행한다. score를 몰래 제외하거나 다른 타입으로 대체하지 않는다.
- 후속 score 조사: 동일 모델의 신규 한국어·영어 18쌍을 언어·질문 유형·순서 조건으로 나눠 총 162개 요청을 실행했다. 정상 score는 두 언어 모두 사전 탐색 기준 미달이며, 영어 지시문이나 choice 전환을 검증된 해결책으로 채택하지 않았다. [상세 결과](../wiki/inference.md#score-확대-대조-평가)를 반영했고 단계 2는 시작하지 않았다.
- 후속 체크포인트 비교: 공식 english·typed-decisions에 같은 162개 요청을 각각 실행했다. english는 영어 score만 사전 기준을 통과했고 한국어는 모든 후보에서 미달했다. 영어 한정 후속 평가 후보는 확보했지만 범용 다국어 score 채택 문제는 남는다. [비교 결과](../wiki/inference.md#공식-체크포인트-비교)를 기록했으며 제품 모델이나 범위를 자동 변경하지 않았다.
- Decider-2B Q8 후속 평가: 원문/동일 JSON 상태 각각 36개 요청을 CPU로 실행해 두 언어 score 기준을 통과했다. 원문 한국어 score 17/18·choice 18/18로 개선됐지만 두 질문 묶음 평균 13.8초, JSON 상태 약 21.3초로 현재 환경의 속도 문제는 남는다. [실행 결과·제약](../wiki/inference.md#decider-2b-q8-대체-후보)을 기록했으며 운영 모델 교체나 단계 2 진행으로 해석하지 않는다.
- Q4 최종 선택: 고정 모델·SHA·런타임은 [채택 결정](../wiki/history/2026-11-13-decider-q4-adoption.md)을 따른다. 한국어 짧은 24건은 게임 choice 4/6·OMP choice 5/6·noul 5/6·score 5/6이며 지연·제품 품질·ARM64 한계는 미해결이다. 후속 진행 승인은 품질 통과나 HTTP 래퍼 구현 완료가 아니다.

## 단계 2 — 독립 풀과 네트워크 검증

- [ ] Caddy 공개/내부 리스너와 Compose 네트워크의 최소 실험 구성을 작성한다.
- [ ] 사용할 탐색 방식을 Caddy 버전·모듈 지원과 함께 확인하고, 컨테이너 교체 후 주소 변화와 재탐색을 시험한다.
- [ ] Gateway 역할의 명시적인 실험용 서버와 실제 Decider Q4 HTTP 래퍼를 사용해 각 풀을 개별적으로 1→2→1로 변경한다. 실험용 서버는 제품 Gateway 구현 완료의 근거로 쓰지 않는다.
- [ ] 준비 전 인스턴스, 종료된 인스턴스, 요청 중인 인스턴스에 대한 라우팅을 관측한다. 복제본 수가 늘었다는 사실만으로 분산 성공을 판단하지 않는다.
- [ ] 호스트 외부 관점에서 내부 리스너·Decider 접근 차단을 확인한다.

**산출물:** 재현 가능한 Compose/Caddy 탐색 검증과 선택 근거.

**완료 조건:** YAML 편집 없이 풀 증감과 준비 상태 반영·분산·외부 차단이 관측된다. 단순 DNS 조회나 Compose health 상태만으로 통과하지 않는다. 불가능한 조합이면 사용자와 구조 변경을 결정한다.

## 단계 3 — Gateway·DB·키 관리

- [ ] Rust·Axum 프로젝트, 설정 로딩, 최소 구조화 로그와 요청 ID, 생존/준비 상태를 구현한다.
- [ ] SQLx와 최초 Migration, 로컬 DB 구성, 키 검증용 해시와 최소 사용량 스키마를 구현한다.
- [ ] 키 생성·조회 범위·폐기·해시 방식과 폐기 반영 시점을 확정하고 운영자 전용 명령을 구현한다.
- [ ] 인증 미들웨어, 원문 키 비저장·로그 마스킹, 사용량 집계·보존·DB 실패 정책을 구현한다.
- [ ] 요청 제한의 키 단위·프로세스 단위·서비스 전체 단위 의미를 확정한다. 두 Gateway에 적용할 정책을 명시한다.

**산출물:** 추론 없이도 실행되는 Gateway 기반, Migration, 실제 키 관리 명령.

**완료 조건:** 프로그램을 실제 실행해 키 발급 → 보호 API 성공 → 잘못된 키 거절 → 폐기 후 거절을 관측한다. 재시작 후 키 상태가 보존되고 원문 키가 DB·로그에 남지 않는다. 제한·사용량의 불확실한 경계는 격리된 회귀 테스트로 검증한다.

## 단계 4 — 추론 요청과 OMP 연동

- [ ] 확정 계약에 따라 `/v1/models`, `/v1/systemone`과 Decider HTTP 클라이언트를 구현한다.
- [ ] 입력·모델 검증, 응답 변환, 안정된 오류 계약과 사용량 기록을 연결한다.
- [ ] 요청 크기·동시 실행·대기·타임아웃 제한과 클라이언트 취소를 구현한다. 제한값과 기준을 문서화한다.
- [ ] OMP에서 실제 모델 목록과 판단 요청을 실행한다. Base URL과 인증 설정을 비밀값 없이 예시로 남긴다.
- [ ] 잘못된 입력·지원하지 않는 모델·추론 오류·시간 초과·취소·과부하를 확인한다.

**산출물:** OMP → Gateway → 실제 Decider의 기능 흐름.

**완료 조건:** 실제 OMP 정상 요청과 오류 시나리오가 계약대로 동작한다. 응답 필드와 confidence 의미를 임의 보정하지 않는다. 단순 HTTP 성공이 아니라 클라이언트가 결과를 정상 소비하는 것을 확인한다.

## 단계 5 — 로컬 통합·복제·복구·교체

- [ ] 단계 2 검증 구성을 실제 Gateway로 전환하고 실험용 서버를 배포 구성에서 제거한다. 실험 파일 자체 삭제는 승인 후 수행한다.
- [ ] 두 Gateway와 공유 DB에서 동시 읽기/쓰기·키 폐기·제한·사용량·잠금 경계를 검증한다.
- [ ] named volume 영속성과 일관된 SQLite 백업 방식을 구현하고 별도 DB로 복구한다. 실행 중인 DB 파일을 무조건 단순 복사하지 않는다.
- [ ] Migration을 단일 실행하고 실패 시 배포가 중단되는 절차를 구현한다. 신·구 코드와 스키마 공존을 확인한다.
- [ ] 실제 요청 부하에서 요청 제외 → 드레이닝 → 교체 → 준비 확인을 구현·관측한다. 연결된 Caddy 탐색 방식이 요청 제외를 어떻게 보장하는지 확인한다.
- [ ] 종료 대기 한도·시간 초과·교체 실패 시 중단·복구를 시험한다. 불투명한 자동 재시도로 실패를 감추지 않는다.

**산출물:** 로컬 전체 실행 구성, DB 백업·복구 및 서비스 교체 절차.

**완료 조건:** 실제 서비스의 풀 증감과 DB 영속성·동시 접근·격리 복구·Migration 실패·요청 중 교체 시나리오를 통과한다. 단일 복제본 교체의 중단 가능성과 추가 복제본의 자원 요구를 명시한다.

## 단계 6 — Oracle ARM64 실측

- [ ] VM 사양·메모리·CPU·스토리지·네트워크 및 실험 범위를 확인하고 실행 승인을 받는다.
- [ ] ARM64 이미지를 빌드하고 운영 DB와 분리된 환경에서 모델 로딩과 실제 추론을 확인한다.
- [ ] 고정 입력·동시성·실행 시간으로 품질, p50/p95 지연, 처리량, 오류율, 메모리와 CPU를 측정한다.
- [ ] Decider Q4 1개와 2개를 비교하고 OOM·CPU 경합·시작 시간·교체 시 최대 자원량을 확인한다.
- [ ] 실측에 근거해 품질·성능 합격 기준과 안전한 동시성·복제본 한도를 사용자와 확정한다.

**산출물:** 재현 조건이 포함된 ARM64 측정 결과와 출시 기준.

**완료 조건:** 정해진 기준을 만족하며 복제·교체에 필요한 자원 여유가 확인된다. 2개 실행이 불가능하면 복제 목표를 완료로 처리하지 않고 모델·VM·범위를 재검토한다.

## 단계 7 — CI/CD와 승인 배포

- [ ] GitHub Actions의 검사·ARM64 빌드·GHCR 게시와 digest 기반 배포를 구성한다. 비밀값은 저장소에 넣지 않는다.
- [ ] 운영 environment 수동 승인과 배포 동시성 제한을 구성하고 실제 저장소 설정의 지원·적용 여부를 확인한다.
- [ ] 백업 → 단일 Migration → 성공 시 서비스 교체 → 준비·기능 확인을 자동화한다. 동시 배포 방지는 Migration 중복 실행 방지와 함께 검증한다.
- [ ] Migration 실패·이미지 시작 실패·준비 확인 실패·드레이닝 시간 초과의 중단과 복구 경로를 구현한다.
- [ ] 실제 공개 HTTPS·내부 네트워크 차단과 비밀값 관리·최소 권한을 점검한다.
- [ ] 운영 실행은 별도 승인을 받은 뒤 진행한다. 데이터 복원은 영향·유실 가능 범위를 설명하고 승인받는다.

**산출물:** 실제 실행 가능한 워크플로와 운영 배포·중단·복구 절차.

**완료 조건:** 승인된 배포 경로를 실제 실행하고 새 서비스 준비 상태와 OMP 기능을 확인한다. 실패 시 새 서비스가 배포되지 않는 경우와 안전한 이미지 복귀 가능 조건을 검증한다. DB 자동 역Migration을 롤백 대용으로 만들지 않는다.

## 단계 8 — 출시 수용과 운영 인계

- [ ] PRD의 모든 FR/NFR에 실제 증거를 연결하고 미확정 필수 항목을 해소한다.
- [ ] 인증·키 폐기·요청 제어·추론 장애·풀 증감·공유 DB·복구·교체·ARM64 배포의 기존 검증 근거를 검토한다. 이후 변경으로 무효가 된 경로만 다시 검증한다.
- [ ] 새 클라이언트 설정, 키 관리, DB 백업·복구, 장애 확인, 배포·중단 절차를 사용자 관점에서 실행 가능하게 정리한다.
- [ ] README의 현재 상태, Wiki의 구현·검증 상태와 한계를 실제 결과에 맞춰 갱신한다.

**산출물:** 요구사항별 수용 결과, 운영 절차, 알려진 한계.

**완료 조건:** 필수 요구사항의 미검증·실패가 없고 운영자가 절차와 위험을 확인했다. 남은 필수 항목을 후속 작업으로 숨겨 출시 완료라고 보고하지 않는다.

## 단계 완료 기록 양식

각 단계가 끝나면 해당 절에 아래 항목을 간결히 추가하고 체크박스를 실제 결과에 맞게 갱신한다. 실행하지 않은 검증은 미실행으로 표시한다.

- 변경: 파일·동작·결정.
- 검증: 실제 명령/시나리오, 환경·버전/리비전, 관측 결과.
- 위험: 실패·미검증·필요 승인.
- 문서: 갱신한 Wiki 또는 계약 링크.
- 판정: 완료 / 진행 중 / 설계 재검토 필요. 다음 단계 실행 여부는 사용자 요청에 따른다.
