# Picksy 단계별 작업계획서

[PRD](../prd.md) · [현재 Wiki](../wiki/wiki.md) · [작업 규칙](../../.omp/AGENTS.md)

## 진행 원칙

- 기존 단계 0~4 완료 결과는 보존한다. 4A 데이터 기반·4B 관리자 인증·4C React 화면과 서버 이미지도 구현·로컬 검증을 마쳤다. 이후 4D와 기존 단계 5~8로 이어간다. 제품 Caddy·Compose 풀은 미구현이다. 서버 전체 명칭은 Picksy Server, Gateway는 내부 추론 중계 역할이다. 단계 5 이후 번호와 과거 검증 링크는 유지한다.
- 사용자와 한 단계씩 진행한다. 해당 단계의 목표·변경 범위 → 구현 또는 실험 → 좁은 검증 → 결과 보고 순서로 수행하고 다음 단계 실행 요청을 기다린다.
- 단계 내부의 구현·검증은 완료 조건까지 수행한다. 실패를 확인한 경우 원인을 해결하거나 설계 변경이 필요한 이유를 제시하며 완료로 표시하지 않는다.
- 사용자 판단이 필요한 제품 범위·보안·운영 선택만 질문한다. 코드·문서·환경으로 확인 가능한 내용은 직접 확인한다.
- `develop`에서 작업한다. 사용자 변경을 보존하고 커밋·푸시는 별도 요청이 있을 때만 한다.
- 검증용 파일·컨테이너·볼륨도 생성·정리 범위를 설명한다. 삭제·덮어쓰기·초기화는 승인 없이 실행하지 않는다. 운영 데이터로 실험하지 않는다.
- 중요한 로직에는 한글로 이유와 제약을 주석에 남긴다. 결과의 장기 지식은 Wiki에, 요구사항 변경은 PRD에 반영한다. 작업 상태는 이 문서에서만 관리한다.
- 외부 계정 준비 E1~E3는 개발 단계와 별개다. 가입·로그인·결제·권한 동의·비밀값 입력은 사용자가 수행하며 도구가 대신 수락하지 않는다. 준비되지 않은 외부 연동을 인증 우회나 가짜 로그인으로 통과시키지 않는다. 선행 조건 없는 개발은 계속할 수 있으나 실제 연동 검증은 해당 외부 준비 완료 후 수행한다.
- 다음 개발 단계는 4D다. E1 준비와 4B 실제 관리자 인증·4C 화면 검증을 완료했다. 외부 계정 준비와 운영·삭제·DB 변경은 각각의 승인 경계를 유지한다.

## 외부 준비 단계 — 계정·콘솔·운영 권한

E1의 개발 콘솔·비공개 설정 준비는 완료했고 E2·E3는 미착수다. 이 절에는 실제 이메일·client secret·토큰·SSH 키·결제 정보를 기록하지 않는다. 사용자 동의와 인증 파일 다운로드는 사용자가 수행하며 실제 값은 비공개 환경에만 보관한다.

### E1 — Google 로그인 개발 설정

- [x] 기존 Life-Bridge와 분리한 Picksy 전용 Google Cloud 프로젝트를 생성·선택했다. 기존 프로젝트는 변경하지 않았다.
- [x] Picksy 브랜딩, 외부·테스트 중 대상, 지정 계정 테스트 사용자와 개발용 웹 OAuth 클라이언트를 준비했다. 로컬 origin·callback은 [로컬 개발 설정](../wiki/local-development.md#google-로그인-개발-설정)을 따른다.
- [x] 관리자 이메일과 client ID·secret·redirect URI를 Git 제외 대상 `.env`에 권한 `600`으로 보관했다. 공개 예시는 빈 값이며 환경변수 연결은 후속 4B에서 구현했다. `.env` 자동 로딩은 없다.
- [x] 사용자가 Google 정책 동의와 인증 JSON 다운로드를 직접 수행했다. 실제 계정·비밀값은 공개 문서·예시에 기록하지 않았다. 실제 로그인·프론트 번들 검증은 후속 4B·4C 결과에 구분한다.

**완료 조건:** 로컬 로그인에 필요한 클라이언트·허용 URL·비공개 설정이 준비됐다. 실제 로그인·비관리자 거부·세션 검증 완료는 단계 4B/4D에서 별도로 판단한다. Oracle 가입은 필요 없다.

### E2 — Oracle 가입·ARM VM 실험 환경 확보

- [ ] 사용자가 Oracle 계정 가입·본인 확인·약관·필요한 결제 수단 등록을 직접 진행한다. 기존 계정이 있으면 재가입하지 않는다.
- [ ] 실제 계정의 무료 자원 조건·리전 가용성·ARM shape·CPU/RAM·스토리지·과금 가능성을 확인하고 사용자 승인 후 실험 VM을 확보한다. 과거 무료 한도나 콘솔 상품 설명만으로 비용 0을 보장하지 않는다.
- [ ] SSH 접근·방화벽·Docker 실행 환경·운영과 분리된 실험 데이터 위치를 준비한다. 관리자·추론 서버 포트를 직접 공개하지 않는다.

**완료 조건:** 승인한 ARM64 실험 자원에 접근 가능하고 자원·비용·데이터 경계가 확인됐다. 이 단계는 운영 배포·운영 DB 생성 또는 변경 승인이 아니다. 단계 6 전에 필요하다.

### E3 — 운영 도메인·Google 로그인·GitHub 배포 권한

- [ ] 운영 도메인·DNS·HTTPS 진입점을 준비하고 운영 OAuth origin/callback을 정확히 등록한다. 로컬 설정과 분리하며 Google 앱 공개 상태·필요한 검증 요건을 실제 콘솔에서 확인한다.
- [ ] 운영 관리자·OAuth·내부 추론 인증 값을 서버 비공개 환경으로 등록한다. 로컬 DB·비밀 설정을 운영 데이터 대용으로 복사하지 않는다.
- [ ] GitHub Actions·GHCR 게시/읽기·VM 배포 접근과 환경 수동 승인·동시 배포 제한을 준비하고 실제 저장소 플랜의 지원을 확인한다.

**완료 조건:** 운영 인증·도메인·배포 권한을 준비했다. 실제 배포는 단계 7의 별도 승인·백업·Migration·서비스 검증 절차를 따른다.

## 단계 0 — 개발 환경과 실험 경계

- [x] Rust 도구체인, Docker 엔진 연결, `docker compose` 사용 가능 여부와 amd64 환경을 확인한다.
- [x] 실행할 프로젝트·포트·환경 변수·개발용 데이터 위치를 정한다. 비밀값이 없는 설정 예시와 로컬/운영 분리 원칙을 준비한다.
- [x] 설치·수정이 필요한 항목은 현재 상태와 변경 범위를 설명한다. 이미 보고된 설치 직후 실패를 재현하려는 것이 아니라 초기 화면 진행 이후의 현재 상태를 확인한다.

**산출물:** 개발 실행 전제와 확인 결과. 아직 전체 앱을 만들지 않는다.

**완료 조건:** Docker 엔진과 Compose를 실제 사용할 수 있고 이후 실험의 자원·데이터 경계가 명확하다. 불가능하면 원인을 해소하거나 환경 작업만 남았음을 보고한다.

### 단계 0 결과

- 판정: 완료. 앱 구현·컨테이너 실행 검증은 아직 수행하지 않았다.
- 환경: `develop`, Intel Mac `Darwin x86_64`, Rust 기본 도구체인 `1.95.0-x86_64-apple-darwin`. `rustc --version`과 `cargo --version` 모두 1.95.0이며 `rustup component list --installed`에서 rustfmt·Clippy를 확인했다.
- Docker: 최초 확인에서 Desktop 소켓이 없어 `open -a Docker`로 설치된 Desktop을 실행했다. 이후 `docker version`에서 Client/Engine 29.9.3, Desktop 4.99.0, 서버 `linux/amd64` 연결을 확인했다.
- Compose: `docker compose version`은 v5.7.0. Desktop 실행 후 `docker compose ls --format json`이 성공하고 `[]`를 반환했다. 실행 중인 Compose 프로젝트는 없었으며 이 결과는 컨테이너 실행 성공을 뜻하지 않는다.
- 자원: `docker info`가 CPU 12개, 메모리 8,321,810,432 bytes를 보고했다. 이는 Docker VM 가용 설정이며 추론 실행 가능성이나 Oracle 자원을 보장하지 않는다.
- 포트: `lsof`로 검사한 시점에 18080·18081 TCP 포트의 LISTEN 항목이 없었다. 향후 실행 전 다시 충돌을 확인한다.
- 산출물: [설정 예시](../../.env.example), [로컬 제외 규칙](../../.gitignore), [로컬 개발 환경](../wiki/local-development.md). 추가 설치·도구체인 변경·실제 `.env`·DB·컨테이너·볼륨 생성이나 삭제는 하지 않았다. Docker Desktop은 실행 상태로 둔다.
- 다음: 사용자 요청 시 단계 1에서 실제 추론·OMP 계약을 검증한다.

## 단계 1 — 추론 후보·OMP 계약과 품질 검증

- [x] 당시 추론 엔진의 사용할 리비전·라이선스·모델 배포 조건·CPU/ARM 지원 조건을 확인한다. ARM은 공식 구성 확인이며 실제 실행은 미검증이다.
- [x] OMP 설치 버전 18.19.0과 동일 버전 공식 태그의 실제 소스로 TypeSafe 호출 경로·인증·요청/응답 필드를 확인한다. 설치 바이너리의 종단 실행과 구분한다.
- [x] Python 추론 서버를 격리된 로컬 환경에서 실행하고 실제 모델 목록·판단 응답·오류를 관측한다. 모델 목록은 404로 확인했다.
- [x] OMP 계약과 당시 엔진 계약의 필드·모델 선택·confidence·오류 차이를 정리하고 초기 Gateway 매핑을 문서화했다. [API 계약](../api-contract.md)을 PRD에 연결했다.
- [x] 한국어·영어 합성 입력의 평가 기준과 결과를 기록한다. score 품질 통과선은 미달이며 일반적인 제품 작업의 품질로 확대 해석하지 않는다.
- [x] 모델 크기·메모리·시작 시간·CPU 제약의 초기 근거를 수집한다. amd64 측정은 ARM 성능으로 일반화하지 않는다.

**산출물:** 실제 응답에 근거한 API 계약, 품질 평가 초안, 고정할 버전과 한계.

**완료 조건:** 실제 추론이 성공하고 OMP 호환 가능 범위와 변환 규칙이 명확하다. 필수 필드의 의미를 알 수 없거나 품질이 목적에 맞지 않으면 후속 구현 전에 재검토한다. 가짜 응답으로 통과시키지 않는다.

### 단계 1 결과

- 판정: 완료. 조사·실험 수행과 모델 선택 완료이며 출시 수용이 아니다. 현재 모델은 사용자 결정으로 [d1 Q4](../wiki/history/2026-11-13-d1-q4-adoption.md)다.
- 이전 후보의 수치·실패·해시·라이선스·당시 승인 상태와 계획서 결과 원문은 [비교 이력](../wiki/history/2026-11-13-inference-comparison.md)에 보존한다. 이전 계약은 [API 이력](../wiki/history/2026-11-13-api-contract-history.md)에 둔다.
- 현재 모델의 성능·한계는 [추론 Wiki](../wiki/inference.md)를 따른다. 단계 1 당시 OMP 종단은 미검증이었으며 단계 4에서 명시적 NativeJudge 경로를 확인했다. 장문·Oracle ARM64·복제 성능은 미검증이고 score를 몰래 제외하거나 다른 타입으로 바꾸지 않는다.

## 단계 2 — 독립 풀과 네트워크 검증

- [x] Caddy 공개/내부 리스너와 Compose 네트워크의 최소 실험 구성을 작성한다.
- [x] 사용할 탐색 방식을 Caddy 버전·모듈 지원과 함께 확인하고, 컨테이너 교체 후 주소 변화와 재탐색을 시험한다.
- [x] Gateway 역할의 명시적인 실험용 서버와 당시 추론 엔진 HTTP 래퍼를 사용해 각 풀을 개별적으로 1→2→1로 변경한다. 실험용 서버는 제품 Gateway 구현 완료의 근거로 쓰지 않는다.
- [x] 준비 전 인스턴스, 종료된 인스턴스, 요청 중인 인스턴스에 대한 라우팅을 관측한다. 복제본 수가 늘었다는 사실만으로 분산 성공을 판단하지 않는다.
- [x] 호스트 외부 관점에서 내부 리스너·추론 서버 접근 차단을 확인한다.

## 단계 완료 기록 양식

각 단계가 끝나면 해당 절에 아래 항목을 간결히 추가하고 체크박스를 실제 결과에 맞게 갱신한다. 실행하지 않은 검증은 미실행으로 표시한다.

- 변경: 파일·동작·결정.
- 검증: 실제 명령/시나리오, 환경·버전/리비전, 관측 결과.
- 위험: 실패·미검증·필요 승인.
- 문서: 갱신한 Wiki 또는 계약 링크.
- 판정: 완료 / 진행 중 / 설계 재검토 필요. 다음 단계 실행 여부는 사용자 요청에 따른다.
