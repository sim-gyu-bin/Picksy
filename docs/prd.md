# Picksy PRD

[작업계획서](plans/implementation-plan.md) · [현재 Wiki](wiki/wiki.md)

단계 1에서 확인한 외부 계약은 [초기 API 계약](api-contract.md), 실제 CPU 관측과 품질 미달 사항은 [추론 Wiki](wiki/inference.md)를 참조한다. 계약 형식의 호환성은 Jev 대체 품질을 보장하지 않는다.

## 1. 문서 상태

초기 제품 요구사항 초안이다. 기존에 합의된 아키텍처를 기준으로 하되, 아래의 세부 동작과 출시 기준은 구현 전 검토할 제안이다. 이 문서 작성은 애플리케이션 구현·배포 승인이나 기술 검증 완료를 뜻하지 않는다.

- 합의된 기술 방향: Rust·Axum Gateway, d1-2B Q4_K_M 별도 추론 서버, Caddy, SQLite·SQLx, Docker Compose, GHCR·Oracle ARM64 배포.
- d1 Q4 모델 선택은 완료했다. 단계 2는 당시 엔진·Python 풀 검증이며 d1 복제 성공이 아니다. 단계 3 완료, 단계 4 진행 승인·미구현이다. 고정 모델·HTTP 런타임와 품질·지연 한계는 [추론 Wiki](wiki/inference.md), 과거 풀 실행 근거는 [History](wiki/history/2026-11-13-pool-validation.md)에 둔다. 운영 검증 완료를 뜻하지 않는다.
- 미확정: 공개 추론 API 세부 스키마, HTTP 래퍼 오류 매핑, 추론 동시성·대기 제한값, 품질·성능 기준.
- 요구사항과 출시 기준의 원본은 이 문서, 실행 순서·체크 상태는 작업계획서, 검증된 현재 지식은 Wiki다. 변경 시 서로 링크하고 본문을 중복 관리하지 않는다.

## 2. 문제와 사용자

개발 도구·게임 서버 등에서 판단·후보 선택·평가 기능을 공통 HTTP API로 호출하려 한다. 각 클라이언트가 추론 엔진의 인증·실행·운영 차이를 직접 다루지 않도록 Picksy가 경계를 제공한다.

첫 검증 클라이언트는 OMP다. 개발 도구와 게임 서버는 향후 활용 대상이며, 첫 출시에서 각각의 전용 SDK나 플러그인까지 제공하지 않는다.

### 핵심 사용자 흐름

1. 운영자가 서버를 구성하고 클라이언트용 API Key를 발급한다.
2. 클라이언트가 인증 후 사용 가능한 모델을 조회한다.
3. 판단 요청을 보내면 Gateway가 인증·입력·제한을 검사하고 d1에 전달한다.
4. 클라이언트는 계약에 맞는 결과 또는 구분 가능한 오류를 받는다.
5. 운영자는 요청 메타데이터와 사용량으로 상태를 확인하고 필요 시 키를 폐기한다.

## 3. 첫 출시 범위

### 포함

- 인증된 모델 목록 조회와 판단 요청, 실제 OMP 연동.
- d1 응답의 의미를 보존하는 Gateway 변환과 오류 처리.
- API Key 발급·폐기, 최소 사용량 집계, 요청 제한.
- 로컬 Compose 실행과 단일 Oracle VM 배포.
- Gateway·d1 독립 풀, 복제본 탐색·준비 상태·요청 분산 검증.
- 운영 DB 영속성, 백업·복구·단일 Migration, 승인된 배포와 교체 절차.

### 제외

- 관리 웹 UI, 결제·요금제, 공개 회원가입, 다중 테넌트 권한 체계.
- 모델 학습·미세 조정, 여러 추론 엔진의 자동 전환, 결과 캐시.
- Kubernetes, 오토스케일링, 다중 VM 고가용성.
- Jev와 동등한 품질 보장, 검증되지 않은 confidence 확률 해석.

## 4. 기능 요구사항과 수용 조건

| ID | 요구사항 | 수용 조건 |
|---|---|---|
| FR-01 | OMP 호환 API | `GET /v1/models`, `POST /v1/systemone`, Bearer 인증을 실제 OMP 요청으로 검증한다. 정확한 요청·응답 스키마는 OMP 소스와 d1 실측으로 확정하며 Base URL의 `/v1` 중복이 없다. |
| FR-02 | 인증과 키 수명주기 | 유효한 키만 보호 API를 호출한다. 키 누락·오류·폐기를 구분해 시험하고 폐기 후 새 요청이 거절된다. 원문 키는 발급 시에만 제공하며 DB에는 검증용 해시를 보관한다. 발급·폐기는 운영자 전용 로컬 명령을 우선 제안하고 공개 관리 API는 만들지 않는다. |
| FR-03 | 입력·모델 검증 | 요청 크기·필수 필드·지원 모델을 검증한다. 잘못된 요청은 d1 호출 전에 거절한다. d1 필드·confidence를 임의로 Jev 의미에 맞추거나 누락된 결과를 꾸며내지 않는다. |
| FR-04 | 실패와 자원 제한 | 입력 오류·인증 실패·제한 초과·추론 실패·시간 초과를 안정된 오류 계약으로 구분한다. 응답에 내부 주소·비밀값을 노출하지 않는다. 요청 크기·동시 실행·대기·타임아웃을 유한하게 제한하고 클라이언트 취소를 처리한다. 자동 추론 재시도는 기본 도입하지 않는다. |
| FR-05 | 사용량 | 키 식별자·요청 ID·시각·결과 분류·소요 시간 등 최소 메타데이터를 기록한다. 원문 키·프롬프트·판단 결과 본문은 기본 저장·로그 대상에서 제외한다. 집계 시점, 실패 요청 포함 여부, 보존 정책은 구현 전 확정한다. |
| FR-06 | 독립 풀과 네트워크 경계 | 공개 Caddy 리스너는 Gateway로만, 내부 리스너는 d1로 라우팅한다. 외부에서 d1나 내부 리스너로 인증을 우회할 수 없다. Gateway와 d1를 개별적으로 1→2→1로 조절해 탐색·준비 상태·분산을 검증하며 목표 운영에서는 YAML 편집이 필요 없다. |
| FR-07 | DB 영속성과 동시 접근 | 로컬·운영 DB를 분리하고 named volume에 운영 DB를 보관한다. 컨테이너 교체 후 데이터가 유지된다. 두 Gateway의 동시 접근에서 잠금·오류·사용량 정책을 검증한다. |
| FR-08 | Migration·복구 | 승인된 배포에서 일관된 백업 → Migration 단일 실행 → 성공 시 서비스 배포를 보장한다. 실패하면 새 서비스 배포를 중단한다. 백업 복구를 격리 환경에서 시험하고 신·구 코드 공존 가능성을 검사한다. 이미지 롤백을 DB 롤백으로 취급하지 않는다. |
| FR-09 | CI/CD와 교체 | 검사 후 ARM64 이미지를 GHCR에 게시하고 고정된 이미지 digest로 배포한다. 운영 수동 승인·동시 배포 제한을 둔다. 요청 제외·드레이닝·교체·준비 확인과 실패 대응을 명시적으로 구현한다. |
| FR-10 | 운영 상태 확인 | 생존 상태와 요청 수용 준비 상태를 구분한다. 요청 ID와 최소 로그로 장애를 추적한다. 추론 서버 미준비·종료·시간 초과를 관측 가능하게 하며 과도한 내부 상태는 공개하지 않는다. |

## 5. 품질·보안·성능 기준

| ID | 기준 | 검증 방법 |
|---|---|---|
| NFR-01 | 데이터·경계 보호 | 외부 접근·잘못된 인증·키 폐기·로그 유출 검사를 실제 구성에서 수행한다. 원문 키·민감 본문이 DB와 로그에 남지 않는다. |
| NFR-02 | 품질을 측정하고 한계를 명시 | 한국어·대표 판단 과제의 고정 평가 입력과 기대 기준을 먼저 정한다. 모델·리비전·환경을 기록해 d1 결과를 평가한다. Jev 비교가 불가능하면 동등성을 주장하지 않는다. |
| NFR-03 | ARM64 자원 예산 내 동작 | Oracle VM에서 처리량·p50/p95 지연·오류율·메모리·CPU를 측정한다. d1 1개와 2개를 비교한다. 수치 기준은 VM 사양과 기준 부하를 확보한 뒤 확정하고, 기준이 없는 상태를 출시 통과로 처리하지 않는다. |
| NFR-04 | 변경 중 데이터 안전성 | DB 교체·복구·Migration 실패·요청 중 서비스 교체 시나리오에서 데이터 손상과 무제한 대기가 없다. 무중단 여부는 실제 관측으로 판단하며 단일 VM 장애 내성을 주장하지 않는다. |
| NFR-05 | 재현성과 유지보수 | 모델·이미지·도구 버전을 식별 가능하게 기록하고 amd64 개발과 arm64 배포를 구분한다. 중요한 제약과 선택 이유는 한글 주석, 장기 지식은 Wiki에 남긴다. |

## 6. 구현 전 결정할 항목

- API 필드·모델 식별자·confidence 의미: 고정 d1 공식 HTTP 실측을 기준으로 한다. score 중앙값·confidence 최대 확률을 보존한다. 공개 HTTP 상태·오류 본문·매핑은 단계 4 Gateway 구현에서 확정하며 [이전 계약](wiki/history/2026-11-13-api-contract-history.md)을 그대로 이식하지 않는다.
- 키 형식·해시·폐기·서비스 전체 제한은 [단계 3 정책](wiki/history/2026-11-13-gateway-key-policy.md)을 따른다. 운영자 로컬 CLI, 난수 키의 SHA-256 검증, 매 요청 폐기 확인, 공유 SQLite의 키별 고정 분 윈도를 사용한다.
- 사용량은 인증된 요청의 최소 메타데이터만 보존하며 자동 삭제하지 않는다. DB 실패 시 503으로 차단하고 미완료 접수를 성공으로 집계하지 않는다. 상세 경계와 검증 상태는 [DB와 배포](wiki/operations.md)에 둔다.
- 모델 준비 상태와 Caddy 탐색은 단계 2에서 Docker DNS·준비 검사·관리 API 재동기화로 당시 구성에서 로컬 검증했다. [당시 이력](wiki/history/2026-11-13-pool-validation.md)과 구분하며 Rust+d1+Caddy 재통합·Oracle 운영 네트워크 검증은 별도다.
- 품질·부하 입력과 합격 기준: 단계 1에서 초안, 단계 6에서 Oracle 실측 후 사용자와 확정. 미달 시 엔진·모델·범위를 재검토한다.
- 종료 대기 시간·교체 실패 시 중단 및 복구 정책: 단계 5에서 실험하고 단계 7 배포 전에 확정.

## 7. 출시 판정

첫 출시는 모든 FR/NFR의 검증 근거가 있고 미확정 필수 기준이 해소된 경우에만 준비 완료로 판단한다. 실제 운영 실행에는 별도 승인이 필요하다.

필수 시나리오는 정상 OMP 요청, 인증 실패와 키 폐기, 잘못된 입력, 과부하·시간 초과·취소, 추론 장애, 독립 풀 증감, 두 Gateway의 DB 동시 접근, 영속성, 백업 복구, Migration 실패, 서비스 교체, 승인된 ARM64 배포다. 구체적인 실행 순서와 완료 기록은 [작업계획서](plans/implementation-plan.md)를 따른다.
