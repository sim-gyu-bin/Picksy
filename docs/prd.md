# Picksy PRD

[작업계획서](plans/implementation-plan.md) · [현재 Wiki](wiki/wiki.md)

현재 구현 계약은 [API 계약](api-contract.md), 실제 CPU 관측과 품질 한계는 [추론 Wiki](wiki/inference.md)를 참조한다. 단계 4의 실제 OMP 연동 성공은 Jev 대체 품질이나 운영 수용을 보장하지 않는다.

## 1. 문서 상태

제품 요구사항과 출시 기준을 관리한다. 단계 0~4의 추론·인증 기반과 4A~4C의 관리자 데이터·Google 로그인·관리 API·React 화면은 구현·로컬 검증을 마쳤다. 화면을 포함한 amd64 서버 이미지를 빌드·실행했으며 ARM64·운영 배포 검증은 아니다. 문서 작성이나 로컬 검증은 운영 배포 승인을 뜻하지 않는다.

- 서버 명칭은 **Picksy Server**다. Rust·Axum 서버가 추론 API와 관리자 로그인·관리 API·React 정적 화면을 함께 제공한다. Gateway는 서버 내부의 인증·요청 제한·추론 중계 역할을 가리킨다.
- 기술 방향: Picksy Server, d1-2B Q4_K_M 별도 Inference Server, Caddy, SQLite·SQLx, Docker Compose, GHCR·Oracle ARM64 배포. 두 서버 풀은 독립적으로 확장한다.
- 프론트는 React·TypeScript·shadcn/ui·Tailwind CSS다. 개발·운영 모두 Vite와 별도 프론트 서버를 사용하지 않는다. esbuild·Tailwind CLI로 정적 파일을 빌드하고 `tsc --noEmit`으로 타입을 검사한다.
- 단계 4의 실제 OMP→Rust→d1, 4A의 데이터·감사·실제 토큰, 4B의 실제 Google 인증·관리 HTTP에 이어 4C의 React 화면·동일 서버 watch 개발·amd64 서버 이미지를 검증했다. 4C 그래프 검증의 합성 이력을 추론 실측으로 간주하지 않는다. 단계 2는 당시 엔진·Python 풀 검증이며 d1 복제 성공이 아니다. 4D와 기존 단계 5 이후는 미착수다. [추론 Wiki](wiki/inference.md), [DB와 배포](wiki/operations.md).
- 공개 추론 계약은 [API 계약](api-contract.md)을 유지한다. 관리자 세션·관리 API는 [별도 4B 계약](api-contract.md#단계-4b-관리자-인증관리-http-계약)을 사용하며 기존 추론 Bearer 인증을 대체하지 않는다.
- 요구사항과 출시 기준의 원본은 이 문서, 실행 순서·체크 상태는 작업계획서, 검증된 현재 지식은 Wiki다. 변경 시 서로 링크하고 본문을 중복 관리하지 않는다.

## 2. 문제와 사용자

개발 도구·게임 서버 등에서 판단·후보 선택·평가 기능을 공통 HTTP API로 호출하려 한다. 각 클라이언트가 추론 엔진의 인증·실행·운영 차이를 직접 다루지 않도록 Picksy가 경계를 제공한다.

첫 검증 클라이언트는 OMP다. 개발 도구와 게임 서버는 향후 활용 대상이며, 첫 출시에서 각각의 전용 SDK나 플러그인까지 제공하지 않는다.

### 핵심 사용자 흐름

1. 운영자가 로컬·운영별 비공개 환경 설정에 관리자 Google 계정과 로그인 설정을 등록한다.
2. 지정된 관리자 한 명이 Google 로그인 후 전체 API 키와 사용량을 조회한다.
3. 관리자는 선택적으로 키 이름을 입력해 생성한다. 서버가 관리용 UUID와 인증 비밀키를 자동 생성하고 원문 비밀키는 생성 직후 한 번만 제공한다. 이름이 없으면 UUID를 표시명으로 사용한다.
4. OMP·게임 클라이언트가 API 키로 모델 목록과 판단 API를 호출한다. 서버는 인증·입력·요청 제한을 검사하고 내부 추론 풀로 전달한다.
5. 관리자는 기간·키별 통계를 확인하고 필요하면 키를 폐기한다. 폐기한 키의 신규 요청은 거절하지만 과거 사용량은 보존한다.

## 3. 첫 출시 범위

### 포함

- 인증된 모델 목록 조회와 판단 요청, 실제 OMP 연동.
- d1 응답의 의미를 보존하는 Gateway 변환과 오류 처리.
- 관리자 웹과 운영자 CLI의 API Key 발급·목록·폐기, 사용량 집계, 요청 제한.
- 로컬 Compose 실행과 단일 Oracle VM 배포.
- Picksy Server·Inference Server 독립 풀, 복제본 탐색·준비 상태·요청 분산 검증.
- 운영 DB 영속성, 백업·복구·단일 Migration, 승인된 배포와 교체 절차.
- 관리자 한 명 전용 Google 로그인, 기간·키별 사용량 화면, 키 생성·폐기, 로그아웃. 로컬 관리자 화면과 컨테이너 정적 제공은 검증했으며 컨테이너의 실제 Google 로그인은 별도 검증 대상이다.

### 제외

- 결제·요금제, 공개 회원가입, 다중 테넌트·역할 관리, 사용자 지정 비밀키 값, 범용 DB 편집·행 삭제 화면.
- 모델 학습·미세 조정, 여러 추론 엔진의 자동 전환, 결과 캐시.
- Kubernetes, 오토스케일링, 다중 VM 고가용성.
- Jev와 동등한 품질 보장, 검증되지 않은 confidence 확률 해석.

## 4. 기능 요구사항과 수용 조건

| ID | 요구사항 | 수용 조건 |
|---|---|---|
| FR-01 | OMP 호환 API | `GET /v1/models`, `POST /v1/systemone`, Bearer 인증을 실제 OMP 요청으로 검증한다. 정확한 요청·응답 스키마는 OMP 소스와 d1 실측으로 확정하며 Base URL의 `/v1` 중복이 없다. |
| FR-02 | 인증과 키 수명주기 | 기존 추론 API의 Bearer 인증을 유지한다. 키 이름은 선택 입력이며 서버가 UUID 식별자와 기존 256비트 난수 비밀키를 자동 생성한다. UUID 식별자나 이름만으로 인증할 수 없다. 원문은 생성 직후 한 번만 제공하고 DB에는 검증 해시만 저장한다. 관리자 웹과 CLI의 발급·폐기는 동일 정책을 사용하며 키 행은 삭제하지 않는다. 폐기 후 신규 요청 거절·재시작 후 상태 보존을 검증한다. |
| FR-03 | 입력·모델 검증 | 요청 크기·필수 필드·지원 모델을 검증한다. 잘못된 요청은 d1 호출 전에 거절한다. d1 필드·confidence를 임의로 Jev 의미에 맞추거나 누락된 결과를 꾸며내지 않는다. |
| FR-04 | 실패와 자원 제한 | 입력 오류·인증 실패·제한 초과·추론 실패·시간 초과를 안정된 오류 계약으로 구분한다. 응답에 내부 주소·비밀값을 노출하지 않는다. 요청 크기·동시 실행·대기·타임아웃을 유한하게 제한하고 클라이언트 취소를 처리한다. 자동 추론 재시도는 기본 도입하지 않는다. |
| FR-05 | 사용량 | 키 식별자·요청 ID·시각·결과 분류·소요 시간에 요청 종류와 실제 입력/출력 토큰 수를 추가한다. 추론과 모델 목록·관리 조회를 구분하고 관리 조회는 추론 통계에서 제외한다. 과거 미수집·실패 등 알 수 없는 토큰 수는 NULL로 유지하고 합계와 미수집 건수를 구분한다. 원문 키·프롬프트·판단 결과는 저장하지 않는다. 기간·키별 요청/토큰/상태 집계를 검증하며 보존 데이터 삭제 기능은 초기 범위에서 제외한다. |
| FR-06 | 독립 풀과 네트워크 경계 | 공개 Caddy 리스너는 Picksy Server로만, 내부 리스너는 Inference Server로 라우팅한다. 외부에서 d1나 내부 리스너로 인증을 우회할 수 없다. Picksy Server와 Inference Server를 개별적으로 1→2→1로 조절해 탐색·준비 상태·분산을 검증하며 목표 운영에서는 YAML 편집이 필요 없다. |
| FR-07 | DB 영속성과 동시 접근 | 로컬·운영 DB를 분리하고 named volume에 운영 DB를 보관한다. 컨테이너 교체 후 데이터가 유지된다. 두 Picksy Server의 동시 접근에서 키·세션·사용량·작업 기록의 잠금·오류·일관성을 검증한다. |
| FR-08 | Migration·복구 | 승인된 배포에서 일관된 백업 → Migration 단일 실행 → 성공 시 서비스 배포를 보장한다. 실패하면 새 서비스 배포를 중단한다. 백업 복구를 격리 환경에서 시험하고 신·구 코드 공존 가능성을 검사한다. 이미지 롤백을 DB 롤백으로 취급하지 않는다. |
| FR-09 | CI/CD와 교체 | 검사 후 ARM64 이미지를 GHCR에 게시하고 고정된 이미지 digest로 배포한다. 운영 수동 승인·동시 배포 제한을 둔다. 요청 제외·드레이닝·교체·준비 확인과 실패 대응을 명시적으로 구현한다. |
| FR-10 | 운영 상태 확인 | 생존 상태와 요청 수용 준비 상태를 구분한다. 요청 ID와 최소 로그로 장애를 추적한다. 추론 서버 미준비·종료·시간 초과를 관측 가능하게 하며 과도한 내부 상태는 공개하지 않는다. |
| FR-11 | 관리자 로그인·세션 | Google 토큰의 서명·발급자·대상·만료와 로그인 요청 결합(state/nonce 등)을 검증한다. `email_verified=true`이며 비공개 환경변수 `PICKSY_ADMIN_GOOGLE_EMAIL`과 일치하는 계정 한 명만 허용한다. 미설정·불일치는 차단한다. 세션에는 Google 고유 식별자와 허용 계정 확인에 필요한 정보를 결합하고 SQLite에는 원문이 아닌 세션 토큰 해시·만료·무효화 상태를 저장한다. HttpOnly·운영 Secure·적절한 SameSite 쿠키, 로그아웃·만료·관리자 설정 변경 후 기존 세션 차단·다중 서버 공유를 검증한다. |
| FR-12 | 관리자 키 관리·작업 기록 | 인증된 관리자가 선택적으로 이름을 입력해 키를 생성하고 이름·UUID·생성일·상태·사용량을 조회하며 확인 후 폐기한다. 이름이 없으면 UUID를 표시하며 이름은 인증·고유 식별에 사용하지 않는다. 원문 키 재조회는 제공하지 않는다. 변경 요청에는 CSRF 방어를 적용하고 API 키만으로 관리 권한을 얻지 못한다. 발급·폐기와 관리자 작업 기록을 같은 트랜잭션으로 처리하며 실패 시 함께 롤백한다. CLI 변경도 이력에 포함하되 관리자 세션 작업과 구분한다. 기록에는 작업 종류·대상 UUID·시각·비민감 행위자 식별만 남기고 이메일·키 원문·인증 토큰은 남기지 않는다. |
| FR-13 | 관리자 화면·동일 서버 제공 | `admin/`의 React·TypeScript·shadcn/ui·Tailwind 화면을 esbuild·Tailwind CLI로 빌드하고 Picksy Server가 정적 파일과 API를 같은 origin에서 제공한다. 개발은 watch 빌드 후 새로고침하며 Vite·별도 프론트 개발 서버는 사용하지 않는다. TypeScript 타입 검사를 별도로 수행한다. Docker 다단계 빌드의 최종 서버 이미지에는 Rust 실행 파일과 화면 파일만 포함하고 Node 실행 서버를 두지 않는다. API 오류가 SPA HTML로 바뀌지 않으며 비인가 상태에서 관리 데이터·키가 노출되지 않는지 실제 브라우저로 검증한다. |

## 5. 품질·보안·성능 기준

| ID | 기준 | 검증 방법 |
|---|---|---|
| NFR-01 | 데이터·경계 보호 | 외부 접근·잘못된 인증·키 폐기·로그 유출 검사를 실제 구성에서 수행한다. 원문 키·민감 본문이 DB와 로그에 남지 않는다. |
| NFR-02 | 품질을 측정하고 한계를 명시 | 한국어·대표 판단 과제의 고정 평가 입력과 기대 기준을 먼저 정한다. 모델·리비전·환경을 기록해 d1 결과를 평가한다. Jev 비교가 불가능하면 동등성을 주장하지 않는다. |
| NFR-03 | ARM64 자원 예산 내 동작 | Oracle VM에서 처리량·p50/p95 지연·오류율·메모리·CPU를 측정한다. d1 1개와 2개를 비교한다. 수치 기준은 VM 사양과 기준 부하를 확보한 뒤 확정하고, 기준이 없는 상태를 출시 통과로 처리하지 않는다. |
| NFR-04 | 변경 중 데이터 안전성 | DB 교체·복구·Migration 실패·요청 중 서비스 교체 시나리오에서 데이터 손상과 무제한 대기가 없다. 무중단 여부는 실제 관측으로 판단하며 단일 VM 장애 내성을 주장하지 않는다. |
| NFR-05 | 재현성과 유지보수 | 모델·이미지·도구 버전을 식별 가능하게 기록하고 amd64 개발과 arm64 배포를 구분한다. 중요한 제약과 선택 이유는 한글 주석, 장기 지식은 Wiki에 남긴다. |

### 모노레포·DB 확장 경계

- 저장소 루트의 `src/`·`migrations/`를 유지하고 `admin/`에 프론트, `deploy/Dockerfile`에 화면을 포함한 서버 이미지 빌드를 구성했다. 제품 Caddy·Compose 구성은 단계 5의 후속 범위다.
- 로컬·운영 모두 Picksy Server가 화면과 API를 제공한다. 프론트는 DB에 직접 접근하지 않는다. 로컬 서버는 로컬 DB·로그인 설정, 운영 서버는 운영 DB·로그인 설정을 사용하며 로컬 DB를 운영에 복사하지 않는다.
- [0002 Migration](../migrations/0002_admin_foundation.sql)으로 `api_keys`의 선택적 이름과 `request_usage`의 종류·실제 토큰, 관리자 세션·로그인 일회성 상태·작업 기록 스키마를 추가했다. 새 격리 v1 DB 업그레이드에서 기존 키·요청·0001 체크섬과 이름·미수집 값의 NULL을 보존했다. 기존 로컬·운영 DB에는 적용하지 않았다.
- 관리자 회원·역할·키 소유권 테이블은 추가하지 않았다. 4A 당시 세션·로그인 일회성 상태는 스키마만 준비했으며 4B에서 발급·검증·만료·로그아웃 런타임을 연결했다. Google client secret·관리자 이메일 실제 값은 프론트 번들에 포함하지 않는다.
- 세션은 로그아웃·만료 시 즉시 접근 불가로 처리한다. 만료 레코드 물리 정리의 주기·범위는 별도 정책과 승인 후 결정하며 사용량·작업 기록·키 행을 함께 삭제하지 않는다.
- 키 폐기는 논리적 사용 중지다. 사용량·작업 기록은 초기에는 보존하며 임의 정리 버튼이나 자동 데이터 삭제를 추가하지 않는다.
- 구 바이너리는 엄격한 Migration 버전 검사 때문에 v2 DB를 새로 열 수 없다. 추가 컬럼을 쓰는 신·구 서버의 운영 롤링·이미지 롤백 호환성을 보장하지 않으며 단계 5~7에서 별도로 해결·검증한다. 실패를 숨기려고 스키마 검사를 해제하지 않는다.

## 6. 확정 정책과 후속 결정 항목

- API 필드·모델 ID·HTTP 오류·상한은 [단계 4 계약](api-contract.md)을 따른다. 실제 OMP의 모델 목록·판단·오류·취소 소비를 확인했으며 score 중앙값·confidence 최대 확률을 보존한다. [이전 계약](wiki/history/2026-11-13-api-contract-history.md)을 그대로 이식하지 않는다. 역할 자동 선택·ChainJudge fallback은 별도 미검증이다.
- 키 형식·해시·폐기·서비스 전체 제한은 [단계 3 정책](wiki/history/2026-11-13-gateway-key-policy.md)을 따른다. 운영자 로컬 CLI, 난수 키의 SHA-256 검증, 매 요청 폐기 확인, 공유 SQLite의 키별 고정 분 윈도를 사용한다.
- 사용량은 인증된 요청의 최소 메타데이터만 보존하며 자동 삭제하지 않는다. DB 실패 시 503으로 차단하고 미완료 접수를 성공으로 집계하지 않는다. 상세 경계와 검증 상태는 [DB와 배포](wiki/operations.md)에 둔다.
- 관리자 이메일 실제 값은 코드·Migration·공개 예시·Wiki·로그에 기록하지 않는다. 공개 예시에는 환경변수 이름과 빈 값만 두고 로컬·운영 실행 환경에 각각 비공개로 주입한다. `.env` 파일과 자동 로딩 지원은 구별한다.
- 관리자 화면에는 별도 회원가입·사용자별 키 소유권·역할 관리가 필요 없다. Google 로그인은 관리 화면용이며 추론 API의 기존 Bearer 인증을 대체하지 않는다. 변경 가능한 관리자 설정과 활성 세션의 허용 계정이 일치하도록 검사한다.
- 관리자·키 관리·프론트의 요구사항은 FR-11~FR-13을 따른다. Google 계정/프로젝트 설정, Oracle 가입·VM 확보, 운영 도메인·인증·배포 권한 준비는 [작업계획서](plans/implementation-plan.md)의 별도 외부 준비 단계에서 다룬다. 계정 가입·결제·권한 동의·운영 변경을 개발 단계에서 자동 실행하지 않는다.
- 모델 준비 상태와 Caddy 탐색은 단계 2에서 Docker DNS·준비 검사·관리 API 재동기화로 당시 구성에서 로컬 검증했다. [당시 이력](wiki/history/2026-11-13-pool-validation.md)과 구분하며 Rust+d1+Caddy 재통합·Oracle 운영 네트워크 검증은 별도다.
- 품질·부하 입력과 합격 기준: 단계 1에서 초안, 단계 6에서 Oracle 실측 후 사용자와 확정. 미달 시 엔진·모델·범위를 재검토한다.
- 종료 대기 시간·교체 실패 시 중단 및 복구 정책: 단계 5에서 실험하고 단계 7 배포 전에 확정.

## 7. 출시 판정

첫 출시는 모든 FR/NFR의 검증 근거가 있고 미확정 필수 기준이 해소된 경우에만 준비 완료로 판단한다. 실제 운영 실행에는 별도 승인이 필요하다.

필수 시나리오는 정상 OMP 요청, 인증 실패와 키 폐기, 잘못된 입력, 과부하·시간 초과·취소, 추론 장애, 독립 풀 증감, 공유 DB·세션, 영속성, 백업 복구, Migration 실패, 서비스 교체, Google 관리자 로그인·거부·로그아웃, 웹 키 생성·폐기·CSRF 차단·작업 기록, 사용량 미수집 값 구분, 실제 관리자 화면, 승인된 ARM64 배포다. 구체적인 실행 순서와 완료 기록은 [작업계획서](plans/implementation-plan.md)를 따른다.
