## 배경과 결정

Gateway 복제본이 같은 SQLite를 사용하므로 키 폐기와 제한을 프로세스 메모리에만 두지 않는다. API 키 관리는 공개 관리 API가 아닌 DB 접근 권한을 가진 운영자의 로컬 CLI로 제공한다. 키 발급 시에만 원문을 출력하고 DB에는 검증용 해시를 저장한다.

키는 OS 난수 256비트 이상의 고엔트로피 토큰으로 만들고 SHA-256으로 검증한다. 매 요청 DB에서 폐기 여부를 확인하며, 이미 허용된 요청을 소급 취소하지 않는다. 비밀번호처럼 사람이 고르는 낮은 엔트로피 입력을 이 해시 정책에 적용하지 않는다.

키별 제한은 DB에 저장한 분당 허용량으로 두 Gateway에 공통 적용한다. 기본은 60회/분이며 발급 시 지정한다. UTC epoch의 고정 60초 구간을 사용하고 허용 여부·카운터 증가·사용량 접수를 동일 쓰기 트랜잭션으로 묶는다. 경계 전후에는 짧은 시간에 두 구간의 허용량이 사용될 수 있다. 이는 토큰 버킷이나 동시 실행 제한이 아니다.

사용량은 인증된 요청의 최소 메타데이터만 기록한다. 인증 실패는 DB 사용량에 넣지 않고, 인증 후 제한 거절은 거절로 기록하되 허용 카운터를 추가 차감하지 않는다. 허용 요청은 접수 상태를 먼저 남기고 완료 상태를 갱신한다. DB 오류에는 503으로 실패하며 인증·제한을 메모리로 우회하지 않는다.

보존 기간은 자동 만료 없이 유지한다. 보존 데이터의 삭제는 별도 승인 대상이며 이번 단계에 자동 삭제 작업을 추가하지 않는다. 원문 키·입력·응답 본문은 사용량 대상이 아니다.

## 대안과 선택 이유

- 프로세스별 제한은 구현이 단순하지만 복제본 수만큼 한도가 늘어나므로 선택하지 않았다.
- 키 캐시는 폐기 지연을 만들므로 초기 구현에서는 쓰지 않는다.
- 고엔트로피 키에 비밀번호용 느린 KDF를 매 요청 적용하는 대신 난수 토큰과 SHA-256을 사용한다. 키 유출을 막아 주는 대안은 아니므로 원문 비저장·로그 제한은 별도로 유지한다.
- 서버 시작 시 자동 Migration 대신 명시적 `migrate` 명령을 사용한다. 운영 백업·단일 실행·배포 순서는 후속 단계이며 자동 Migration으로 우회하지 않는다.

## 결과·단점·검증 상태

SQLite 쓰기가 인증된 요청의 병목이 될 수 있다. 현재 단일 VM의 작은 판단 서비스에 맞춘 선택이며 부하 처리량은 별도 실측해야 한다. HTTP 응답 전송과 DB 기록을 하나의 원자적 작업으로 만들 수 없으므로 접수 후 중단된 요청은 미완료로 남는다. 완료 기록이 실패하면 성공으로 포장하지 않는다.

이 기록은 구현 선택의 근거다. 실제 명령·코드와 검증 완료 여부는 [DB와 배포](../operations.md), [작업계획서](../../plans/implementation-plan.md)에서 확인한다. 운영 DB·ARM64·추론·OMP 연동의 검증 근거가 아니다.
