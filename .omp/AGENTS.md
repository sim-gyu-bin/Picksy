# Picksy 작업 규칙

인증·데이터·실행의 핵심 경계는 [RULES.md](RULES.md)를 따른다. 이 문서는 개발을 이어가는 방법을 안내하며 작은 변경마다 전체 절차를 반복하게 하는 체크리스트가 아니다.

## 기본 원칙

- 응답·작업 설명·사용자 대상 문서·직접 작성하는 코드 주석은 한국어로 작성한다. 코드 식별자·API·프로토콜·필수 도구 지시문은 원문을 유지한다.
- 구현 전 관련 코드와 기존 패턴을 확인한다. 요청 범위만 변경하고 불필요한 추상화·의존성·겸사겸사 리팩터링을 추가하지 않는다.
- 설계 합의, 구현 완료, 실행 검증 완료를 구분한다. 추정과 미검증 내용을 사실로 보고하지 않는다.
- 이후 개발은 `develop` 브랜치를 기준으로 한다. 사용자 변경을 덮어쓰지 않으며 커밋·푸시는 명시적인 요청이 있을 때만 수행한다.

## 유연한 작업 흐름

- 한 단계씩 진행하되, 요청된 단계 안의 수정·원인 분석·관련 검증은 중간 재승인 없이 이어서 완료한다. 다음 단계 실행과 제품 범위·운영 위험이 달라지는 선택은 사용자 요청을 따른다.
- 규칙·스킬 변경은 현재 세션에서 파일을 직접 읽어 반영한다. 스킬이 아직 목록에 없으면 `.omp/skills/<name>/SKILL.md`를 읽는다. 자동 재탐색 여부와 직접 지침을 읽고 수행할 수 있는지는 구분하며 새 세션을 기본 해결책으로 제시하지 않는다.
- 이미 확인한 설계·근거·검증은 관련 변경이 없는 한 재사용한다. 작은 수정은 영향받는 경로만 검증하고, 실패 수정 후에는 해당 검사를 다시 실행한다. 매번 전체 테스트·외부 문서 조사·Wiki 이력 작성을 요구하지 않는다.
- 외부 사양이 구현 판단에 영향을 주거나 버전·호환성이 불확실할 때만 `source-verification` 스킬을 사용한다. 사소한 내부 수정 때문에 외부 조사를 반복하지 않는다.

## Rust 구현과 검증

- 기존 Rust 관례와 프로젝트 설정을 우선한다. 아직 없는 도구체인 파일·검사 스크립트·환경변수가 존재한다고 가정하지 않는다.
- 단위 테스트는 해당 모듈 가까이에, 공개 동작의 통합 테스트는 `tests/`에 두는 Rust 관례를 기본으로 한다. 별도 테스트 구조나 프레임워크를 선제 도입하지 않는다.
- 중요한 인증·동시성·취소·시간 초과·DB 경계는 사용자에게 보이는 동작으로 검증한다. 내부 배선이나 문구만 고정하는 테스트는 피한다.
- 테스트는 격리된 DB와 합성 데이터를 사용하며 운영 DB·실제 비밀값·유료 API를 자동 연결하지 않는다.
- Rust 프로젝트 구성 시 로컬과 CI의 정식 검사 진입점을 맞춘다. 작업 중에는 변경에 맞는 좁은 검사를 쓰고, 정식 검사는 포맷·Clippy·테스트를 포함한다. 실패를 광범위한 `allow`나 검사 제외로 숨기지 않는다.

## 한글 주석

- 새로 작성하거나 동작을 변경하는 코드에는 이해에 필요한 한글 주석을 함께 작성·갱신한다. 코드 변경으로 틀린 주석은 수정하거나 제거한다.
- 주석은 코드가 무엇을 하는지 반복하기보다 **왜 이렇게 구현했는지**, 지켜야 할 조건, 실패 시 영향과 주의점을 설명한다.
- 인증·권한 경계, 동시성·잠금, 트랜잭션·Migration, 타임아웃·취소·드레이닝 등 실수의 영향이 큰 로직에는 비자명한 제약과 선택 이유를 남긴다.
- 외부 API 연동에서는 단위·값의 의미·변환 이유·호환성 제약을 설명한다. 확인하지 않은 서버 동작을 보장하는 주석은 쓰지 않는다.
- 공개 API와 핵심 타입에는 필요에 따라 Rust 문서 주석(`///`, `//!`)을 사용해 책임·입출력 의미·오류 조건을 설명한다. 자명한 접근자나 모든 줄에 의무적으로 주석을 붙이지 않는다.
- 이름과 함수 분리로 해결할 수 있는 난해함을 긴 주석으로 덮지 않는다. 구현을 먼저 읽기 쉽게 만든다.
- 긴 설계 배경과 결정 이력은 Wiki에 두고 코드에는 필요한 핵심 제약과 관련 문서 경로만 남긴다. 변경 날짜·작업자 이름·작업 일지를 코드 주석에 누적하지 않는다.
- 비밀값·토큰·개인정보·운영 데이터는 주석·예제·로그에도 기록하지 않는다. 자동 생성 파일과 외부 라이브러리의 주석은 번역 목적으로 수정하지 않는다.

## Wiki 활용

- 개발·기술 검토 전에 `.omp/skills/llm-wiki/SKILL.md`의 Query 절차에 따라 `docs/wiki/wiki.md`에서 관련 주제만 읽는다.
- 재사용할 지식이나 중요한 결정이 생기면 Ingest 절차로 기존 문서를 우선 갱신한다. 현재 지식과 결정 이력을 분리하며 사소한 변경을 모두 기록하지 않는다.
- Wiki와 구현이 다르면 실제 코드·설정·검증 결과를 확인한다. 승인된 설계를 코드에 맞춰 임의 변경하지 말고 불일치를 보고한다.

## 검증과 안전

- 동작 변경 후 해당 경로를 확인하는 가장 좁은 테스트·명령·시나리오를 실행한다. 실행하지 못한 검증과 남은 위험을 명시한다.
- 문서 변경은 링크와 내용의 일관성을 확인한다. 문서 작성만으로 애플리케이션이나 배포가 검증됐다고 표현하지 않는다.
- 파일·디렉터리·저장 데이터의 삭제, 덮어쓰기·초기화는 대상과 범위를 설명하고 명시적 승인을 받는다. 요청받은 문구·코드 편집과 파일 자체 삭제를 구분한다.
